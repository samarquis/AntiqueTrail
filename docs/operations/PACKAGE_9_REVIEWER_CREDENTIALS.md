# Package 9 reviewer credential operations

Status: **NO-GO / provider disabled by default**. No verifier, relying-party configuration, qualification evidence, or credential has been fabricated by the repository.

An authorized configurator must provision a pending reviewer identity from real qualification evidence, accept the exact HTTPS origin, relying-party ID, verifier key ID, and evidence digest, deploy the verifier identity and secret, and only then set `REVIEW_CREDENTIAL_PROVIDER_ACCEPTED=true`. The configured origin must exactly match the application origin. Use the reviewed bounded timeout in `REVIEW_CREDENTIAL_TIMEOUT_MS`.

Enrollment, management, recovery, and appeal assertion require separate high-entropy capabilities generated and delivered by the trusted capability service. Only the SHA-256 token hash is stored. The Edge endpoint exchanges that capability without requiring or consulting an Antique Trail account session, username, or discoverable credential. Management capabilities expire within ten minutes; setup and recovery capabilities expire within thirty minutes. Never place raw capabilities in URLs, logs, analytics, support messages, or durable receipts. The URL fragment must be scrubbed before exchange.

One setup or recovery capability authorizes exactly two successful, distinct non-discoverable credential registrations through sequential five-minute, server-generated challenges. An expired attempt may be replaced while the capability remains valid; a completed first registration resumes only with that same capability. The capability is consumed atomically by the second verified registration and cannot authorize a third. Only the verifier service can record credential ID/public-key digests and provider verification IDs. The browser cannot submit a credential count or verification result. The identity becomes active only when the database counts two active durable credential rows.

Every independent appeal decision requires a new case-bound assertion challenge. Credential list and revoke each require a management capability plus a fresh assertion, then atomically consume both. The provider response must echo the challenge, match the accepted verifier key, identify an active credential owned by the assigned reviewer, and advance its signature counter. Challenges and provider verification IDs are one-use; exact lost-response retries return the prior receipt. Recovery issuance revokes every old credential and live capability before the same recovery capability enrolls exactly two replacements. Credential revocation consumes outstanding assertions and disables the reviewer whenever fewer than two active credentials remain.

Before enabling enrollment, an authorized configurator must install an evidence-bound, environment-specific credential-reuse HMAC key. Revocation, recovery, and relationship-end cleanup fail closed if no accepted key exists. Cleanup HMACs the credential identifier, unlinks assertion and command references, and deletes the public-key digest, provider identifiers, signature counter, and reviewer-linked credential row. Only the keyed reuse marker and key version remain for at most 90 days; registration checks all retained key versions, and the lifecycle worker deletes expired markers and retired keys in bounded, skip-locked batches. Revoking the verifier disables all independent reviewers, consumes proof, and revokes live capabilities. The lifecycle worker removes used/expired capability hashes and challenges within 24 hours. Administrator appeal separation remains unchanged.
