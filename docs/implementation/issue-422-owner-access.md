## A: approved primary Owner grant

Reuse `partner_private.listing_claims`, its verified authority signals, existing claim approval transaction, partnerships, partner grants, app role grants, receipts, and audit chain. Add the `store_owner` app role, permit that exact-store role in existing grant constraints, and retain existing Representative paths unchanged.

`app_public.owner_admin_approve_claim(p_claim_id uuid, p_store_id uuid, p_expected_version bigint, p_idempotency_key text)` confirms the exact claim boundary, checks Site Admin/current session/recent MFA, verified claimant email and enrolled MFA, and synthetic-alpha store scope. It consumes the existing approval command and converts only the grants just created by that transaction to `store_owner`. It returns `{role: "Store Owner", storeId: uuid, claimId: uuid}`. Unchanged replay returns the same identifiers without minting another grant. Mismatched replay, missing evidence, self-approval, wrong boundary, real store, and unauthorized actor fail closed. Boundary correction uses the existing reviewed listing/claim process before approval; this command never silently moves authority evidence to a different store.

The existing exact-claim revocation helper also revokes `store_owner` app grants. Its existing Site Admin caller, claim events, partner revocation receipts, and audit chain remain authoritative. Revoking one claim affects that store only; across-store revocation uses one audited exact-claim command per approved store.

## B: workspace scope

`app_public.owner_list_stores()` returns `{role: "Store Owner", stores: [{storeId: uuid, name: string}]}` for current approved synthetic Owner grants only. An empty grant list is an access denial. Require active session, current consent, verified email, MFA/recent auth, and existing privileged audit-anchor freshness.

`app_public.owner_select_store(p_store_id uuid)` validates the current grant and returns `{storeId: uuid}`. The tab retains that requested store and sends `x-owner-store-id` on each Portal and promotion RPC, and through the media HTTP/Edge user boundary. Selection never mutates a shared session target: choosing another store in another tab cannot silently redirect this tab’s mutation. Client store choice is a request, never authority. `portal_private.require_portal_scope()` rechecks the requested Owner grant, approved claim, immutable approval marker, active partnership, synthetic invitation, revocation receipt, session, assurance, provider-confirmed email, and synthetic stage on every request. A revoked or foreign requested scope denies rather than falling back. Existing Representative resolution remains unchanged when no Owner scope is requested.

Owned endpoints are existing Portal home, hours read/save, managed fields, controlled-change submission, media history/capacity, updates, official links, support, and listing preview through their existing shared scope helper. Existing photo/review/promotion provider gates remain intact; this issue adds no external publication, billing mutation, team authority, analytics source, or Site Admin console access. Team and billing contracts remain #424/#425. Direct wrong-store selection, anonymous/revoked/stale sessions, and Administrator RPC attempts must deny. No browser table grants are added. Legacy media reservation replay, upload actor reads, and withdrawal check requested Owner scope before success; independent current Administrator authority is preserved when no Owner scope is requested. Denied Owner list/selection/Portal/media requests emit structured PostgreSQL LOG events containing only opaque IDs and fixed operation codes; server logs survive transaction rollback. CI verifies the emitted exact-scope denial after the rolled-back pgTAP run. Hosted log collection/retention remains a deployment gate.

## C: workspace entry

Enabling the isolated synthetic composition resolves the display role through `owner_current_role()` after registering the session; a client role or feature flag cannot create authority. Administrator display-role precedence is retained when an account also owns stores; same-user registration/refresh preserves a still-authorized selection. Invalid/denied approval or selection uses SQLSTATE `42501` with `owner_access_unavailable`; malformed commands/replays use `22023`; existing approval conflict/version errors retain their established contract. Portal denial remains `42501 / portal_unavailable`.

Add an authenticated `/owner/stores` selection page consuming B, displaying the distinct Store Owner role and only server-returned stores. Selection enters the existing Store Portal. Loading, unavailable, selection failure, and revoked access remain reason-neutral and retryable. Existing server-checked Portal route guard remains authoritative. Sign-in uses existing provider/MFA/session flow; display metadata never grants access.
