## Hosted log guidance

If a valid canonical list/details request fails after confirming the actual allowed Origin and request path, and existing read-only Supabase access is available, use Studio Logs with the observed time range, Edge Function log type, `public-catalog` pathname, `POST` method, and status. Inspect invocation status and duration; correlate associated console output only when useful. Record only the operation, status, timestamp, source binding, and safe correlation ID if one exists. Do not publish invocation headers or bodies. An empty result does not establish that no activity occurred; the time range and log type must match, and the event must have been recorded. A successful observation needs no hosted-log read; record status, route, source binding, and safe correlation ID only when exposed. A rendered route alone does not establish HTTP status or backend identity. If existing log access is unavailable after a reproduced failure, mark that evidence unavailable and keep the cause unresolved; request no new provider rights.

Supabase's current [Logs in Studio guide](https://supabase.com/docs/guides/observability/logs) documents time-range, log-type, status, method, and pathname filters, and cautions that an empty result is not proof of no activity. The [Edge Function logging guide](https://supabase.com/docs/guides/functions/logging) distinguishes invocation request/response data, including status and duration, from platform events, uncaught exceptions, and custom logs. Supabase removed Management API `logs.all` on 2026-09-23; the Dashboard Logs Explorer is unaffected, and the replacement Management API `logs` endpoint accepts ClickHouse SQL, as documented in the [specific changelog entry](https://supabase.com/changelog/48235-migration-of-supabase-management-api-logs-all-analytics-endpoint-to-logs-endpoint).
