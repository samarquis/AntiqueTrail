## Implementation and acceptance boundaries

Existing release stages and receipts retain their original meaning. Internal admission must not set public/private-beta/paid activation receipts to passed or enable external publication. Public signup, real email delivery, real participants, existing beta accounts, live external providers, spending and paid activation remain prohibited. Use provider-created controlled synthetic identities without delivery; treat unavailable provider-dependent paths as blocked. Supporting login does not imply email delivery, account recovery or social-provider acceptance.

The narrowly scoped missing `public_catalog_gateway` membership in `authenticator` may be repaired by a forward-only migration with fresh independent authorization review. Do not change direct-table privileges or replace the gateway identity with service_role. Internal assessment may use only the approved synthetic capabilities expressly listed in its typed record. Capability checks must be evaluated at the real server boundary, including direct RPC, storage, export/download, offline-grant and worker paths; UI hiding is insufficient. Existing role/store/account and MFA restrictions still apply.

Provisioning and revocation must be trusted operator operations inaccessible to browser roles. Record the actual isolated project identity from trusted deployment configuration, never a client-supplied project or origin claim. Validate the authorization against the actual current deployment/source/artifact/configuration record; accepting self-consistent values supplied by an untrusted caller is insufficient. Restrict the internal lookup and its grantable operations to least-privileged private schema functions; do not add broad definer privileges to resolve errors.

Before issuing the first internal record, preserve the owner decision, protected-host checks, exact candidate and private fixture manifest. A record is valid for no more than 24 hours, with explicit revocation and no automatic renewal. Expiry/revocation immediately denies new private access using authoritative server checks even if a provider JWT has not expired; bounded cleanup is retryable and failure does not reopen access. Existing valid offline grants must not extend internal access beyond the internal expiry, and reconnect must enforce revocation. Do not claim the server can instantly reach a disconnected device; apply the existing offline-expiry and purge contract.

Acceptance requires missing/expired/revoked/mismatched record denials; an unlisted identity, foreign store/account, insufficient MFA and stale session remain denied; permitted synthetic roles can perform only the scoped operations. Exercise duplicate provisioning and cleanup safely, and verify that every original public/shared/paid gate remains unchanged. Independently review the exact executable candidate and run required hosted checks before deploying. Bind the rebuilt protected Preview and updated isolated schema before resuming the existing scenario register. Report synthetic hosted results separately from provider, professional and human evidence.
